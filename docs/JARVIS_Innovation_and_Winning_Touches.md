# J.A.R.V.I.S. — Innovation, Winning Touches & Data Approach

> Companion to `JARVIS_Features.md`. The base features are already defined there.
> This file adds the **unique innovations** and **winning touches**, and defines **how data is handled (no regular database)**.

**Product line:** *"Other tools show you 247 alerts. J.A.R.V.I.S. shows you the 1 cause, the 1 fix, and the next failure before it happens."*

---

## 0. Data Rule: NO Regular Database

Do **not** use MySQL, PostgreSQL, MongoDB, Firebase, SQLite or any normal table-based database. Do **not** use generic downloaded or random fake datasets.

Use this custom approach instead:

1. **In-Memory Temporal Knowledge Graph**
   - Services, events, and incidents are stored as **nodes and edges in a graph object in memory**.
   - Edges carry meaning: `depends_on`, `caused_by`, `precedes`, `affects`, `similar_to`.
   - Every edge has a **weight** (strength of relationship) and a **timestamp**.
2. **Event Stream Store (append-only)**
   - Events live in an append-only array, like an event log. Nothing is edited or deleted; state is rebuilt by replaying events.
   - This also powers **time travel** and **timeline replay** for free.
3. **Ring Buffers for Metrics**
   - Each service keeps fixed-size rolling buffers (latest N points) for CPU, latency, error rate, memory, connections. Used by the prediction engine.
4. **Procedural Scenario Generator (not static fake data)**
   - Data is **generated by a seeded simulation engine** that models service behavior: each service has a health state, a load level, and dependencies.
   - When a service degrades, the engine **naturally produces** cascading logs, latency growth and errors downstream, with realistic noise, random jitter, retries and unrelated "decoy" alerts.
   - Same seed = same demo every time (safe for presentation). Different seed = different incident.
5. **Optional persistence:** only the browser's `localStorage`/`IndexedDB` to save the last session and uploaded files. No server database.

**Mandatory data realism:**
- Include **decoy alerts** (unrelated noise) so the system must prove it can separate real connections from fake ones.
- Include **misleading symptoms** (the loudest alert is NOT the root cause).
- Include **delayed effects** (some failures appear minutes after the cause).
- Use realistic log formats: stack traces, HTTP codes, trace IDs, user IDs, region tags.

## 1. Core Innovations (Unique Differentiators)

### I1. Incident DNA Fingerprint
- Every incident gets a **visual fingerprint** (a unique pattern/barcode) built from: origin service, spread pattern, speed, error types, severity.
- New incidents are compared to stored fingerprints: **"87% match with Incident #14 (DB connection exhaustion)."**
- Gives instant recognition and a fast fix suggestion from past cases.
- Show fingerprints side by side in a comparison view.

### I2. Counterfactual "Rewind & Fix" Simulator
- User picks a moment on the timeline and a fix (example: "restart Auth DB at 10:42").
- The system **re-runs the simulation** with that fix applied and shows what would have happened: alerts avoided, users saved, minutes saved.
- Proves the recommended fix works **before** the user applies it.
- Display: "Without fix: 4,200 users affected → With fix: 310 users affected."

### I3. Predictive Failure Cone (Future Forecast)
- On the timeline, the future is drawn as an **expanding cone** from "now": the narrow part is near-term (high certainty), the wide part is far-term (lower certainty).
- Predicted failing services appear on the graph as **dashed orange nodes** with probability and ETA.
- Metric charts show a **projected dotted line** crossing the danger threshold, with a countdown: **"Threshold breach in 04:12."**
- Each prediction includes the **evidence** (which log patterns and trends triggered it).

### I4. Cascade Propagation Wave
- When a service fails, an **animated ripple wave** moves along the graph edges to downstream services, with speed matching the real delay.
- Shows *how* the incident spread, not just *what* broke.
- A "Wave Speed" metric: "Failure spread across 5 services in 6 minutes."

### I5. Explainable Confidence (Evidence Cards)
- Every conclusion has **Evidence Cards**: the exact logs, timings and graph paths that support it.
- A **confidence breakdown bar** per cause: time order, dependency path, pattern match, history match.
- Includes a **"What would change my mind?"** line: the data that would lower confidence. This shows honest, justified reasoning.

### I6. Noise vs Signal Separation
- Each event gets a **Signal Score**. Low-score events are shown faded as "likely unrelated noise."
- Counter: **"247 raw alerts → 38 relevant events → 1 incident."**
- Decoy alerts are explicitly called out as "Rejected: reason."

### I7. Incident Story Mode (Auto Narrative)
- Generates a **human-readable story** of the incident:
  *"At 10:41 the Core DB hit its connection limit. Within 2 minutes, Auth Service began timing out, causing login failures for 1,200 users. By 10:46, payments were failing..."*
- **Two views with a toggle:** *Engineer view* (technical details) and *Executive view* (impact, cost, status in simple words).

### I8. Early Warning "Heartbeat"
- A live **ECG-style heartbeat line** for the whole system at the top of the dashboard.
- Healthy = steady rhythm; early warning = irregular rhythm; incident = flatline/alarm.
- Instantly communicates system health to judges.

### I9. Digital Twin What-If Lab
- A sandbox copy of the system graph. User can **break, overload or fix any service** and watch the predicted effect.
- Preset experiments: "What if Payment Gateway goes down?", "What if traffic doubles?", "What if Auth DB is slow for 10 minutes?"
- Output: blast radius, users affected, time to cascade.

### I10. Self-Healing Dry Run
- The system proposes an **automated remediation plan** and runs it as a dry run on the digital twin.
- Shows step-by-step: "Step 1: Increase pool size → Step 2: Restart Auth → Step 3: Replay failed payments," with before/after health.
- Marked clearly as **simulation** (no real systems touched).

## 3. Suggested Engine Logic for Innovations

- **Fingerprint match:** compare vectors of `[origin service, spread order, speed, error types, severity]` using cosine similarity.
- **Counterfactual:** clone the graph state at time T, apply the fix, re-run the simulation forward, and diff the outcomes against the original run.
- **Prediction:** per-metric trend (slope over the ring buffer) → time to threshold; propagate probability down the dependency edges with decay, `P(child) = P(parent) * edge_weight`.
- **Signal score:** weighted mix of dependency proximity to the root cause, time proximity, and pattern similarity; low scores are marked as noise.
- **Confidence:** normalized weighted sum of evidence signals, shown with its breakdown.
- **Story generator:** template-based narrative filled from the incident timeline and impact numbers (no external API required).
